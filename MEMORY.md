- [07-03-2026] decision: Set-only listings store no seller-entered per-size price. The form hides the per-size price inputs when "sell as set only" is checked (ListingSizeRow `showPrice`; unchecking clears row prices so switching to individual forces re-entry), and the server (variantRowsPayload in sell.ts) stamps every variant's `price = listings.bundle_price`. This keeps the variant-level browse price filter (MEMORY 07-02) UNCHANGED: a set-only listing filters as a single-priced item at its set total (a $400 set is excluded by a max-$200 filter), while individual/either keep real per-size prices so the size+price coupling still holds (a $600 size-8 stays excluded by max-$400). No schema migration — `listing_sizes.price` stays NOT NULL. Chose this over (A) a denormalized `listings.min_price` column — rejected because it decouples size from price (would wrongly surface the $600 size-8 via a cheaper size in the same listing) — and over (B) a Postgres RPC/view — rejected as a heavy rewrite of the count/pagination/filter layer; both became unnecessary once set-only variants carry the set total. `bundle_price` stays on `listings` as the display source of truth (and the only home for `either`'s discount); the mirrored variant price is filter-only and never shown. Invariant "set_only ⇒ every variant.price == bundle_price" is app-enforced on create + update (variantRowsPayload runs on both; a CHECK can't reference another table and a trigger was avoided for simplicity), and read/delete need nothing extra (read is consistent by construction, delete cascades).

- [07-06-2026] decision: Multi-write listing mutations are atomic via Postgres RPCs (security invoker, `set search_path=''`, granted to authenticated), NOT client-side supabase-js sequences — because supabase-js talks to stateless PostgREST and can't hold a transaction across calls. `mark_listing_sold(p_listing_id)` (migration 010) flips listings.status + all listing_sizes.status in one tx (mirrors the old `.eq(user_id)` guard: `where user_id = auth.uid()` + row_count=0 → "Listing not found"). `update_listing_with_variants(p_listing_id, p_listing jsonb, p_variants jsonb)` (migration 011) updates the listing row + reconciles variants (delete removed / update price+sort_order preserving status / insert new via jsonb_to_recordset), replacing the TS `syncListingSizes` diff (now deleted, along with ExistingVariant type + the `sizes` embed in updateListing's existing-row select). sell.ts's updateListing now uploads images → calls the RPC → deletes ORPHAN images only AFTER the atomic commit (was before, which orphaned them on a mid-sync failure). Image upload/cleanup stay in the action (storage can't join a DB tx). Rejected an ORM (Drizzle/direct pg) that would allow TS-side transactions: conflicts with AGENTS "no ORM", loses RLS as the free ownership gate (direct conns bypass RLS), adds a 2nd data-access path + serverless pooling — disproportionate for two low-frequency partial-write windows. Verified with a BEGIN…ROLLBACK smoke test in the Supabase SQL editor (all checks PASS: variant diff, sold-variant status preserved, atomic rollback of listing row on a failed variant insert, mark-sold cascade, non-owner rejection). Cost: each behavior change to the variant-diff rules now means a new migration (`create or replace`) + schema.sql edit.

- [07-07-2026] decision: Browse listings grid is pure CSS — `grid-cols-[repeat(auto-fill,minmax(15rem,1fr))]` in ListingsGridWrap (now a tiny Server Component) replaced the ~100-line client-side ResizeObserver/rAF measuring version. `auto-fill` (not `auto-fit`) keeps empty tracks so sparse rows stay left-aligned in a full row; `1fr` max makes the column count derive from the 15rem min (dense packing, the old JS behavior) with tracks stretching to fill — accepted trade-off: no hard 18rem card cap (cards stretch ~1-2rem past it at 3+ cols, full-width at 1 col on phones). No hydration layout shift, no per-resize JS.

- [07-22-2026] decision: Buyer wishlist Phase 2 source-of-truth is T1 (server-authoritative when signed in) fed WITHOUT regressing the (main) PPR shell: instead of awaiting the wishlist in layout.tsx (which would make every (main) page dynamic and kill the static prerender the navbar's Suspense'd auth read protects), a Suspense-wrapped `WishlistServerSync` server component (sibling of the visible tree inside `WishlistProvider`) fetches getCurrentUser + getUserWishlist and streams the result into the client provider via a tiny `WishlistHydrator` client leaf (calls `syncFromServer` once in an effect, passing isAuthenticated + userId + serverItems). Provider reconciles local vs server after BOTH localStorage hydration and the server payload land, re-running once per auth-state flip (guarded by `lastSyncedAuthRef`), because child effects fire before parent effects and a naive sync would clobber un-hydrated local items. Reconcile keys off a top-level `ownerId` in the local cache (the account it mirrors; null = a pure guest cache) plus the CURRENT session, never device history, via the pure `planWishlistReconcile` (wishlist-storage.ts): signed-out or server-read-failed → keep-local (cache untouched); signed-in with a guest (null-owner) or same-user cache that has local items → merge (upsert-ignore, then adopt the canonical list); signed-in with a foreign-owner cache OR nothing local to merge → use-server (a foreign-owner cache is discarded wholesale, never partially merged). getUserWishlist failure degrades to serverItems=null (keep local mirror), NOT a throw, so a transient DB error never trips (main)/error.tsx or wipes the drawer. Merge dead-IDs use a `security definer` `existing_listing_ids(uuid[])` SQL function (migration 020) — a buyer's RLS view of listings only shows active/sold/own, so a plain select can't tell a `removed` row (keep, FK still passes) from a hard-deleted one (drop, or the FK insert aborts the batch); the definer read returns physically-existing ids regardless of status, chosen over per-row-tolerant upserts and over a buyer-visible filter (which would silently drop removed items, violating keep-everything). Optimistic add/remove while signed in fire the DB write in the background and are NEVER reverted on failure — a brief non-blocking toast is shown and the change self-heals on the next sign-in merge (a previously failed remove may reappear, accepted). Sign-out KEEPS the local mirror and leaves `ownerId` untouched (edits made while signed out inherit it), so a later same-user sign-in re-merges them while a different KNOWN-owner sign-in discards the whole cache; only the guest (null-owner) case is not identity-verified (a guest cache merges into whoever signs in first). The earlier `merged` flag was REMOVED — the `ownerId` model supersedes it. Auto-reopen (§5.3) reads `wishlist=open` from `window.location.search` in a mount effect and strips it via `window.history.replaceState` — NOT `useSearchParams`/`router.replace` — because the provider + sheet are layout-root client components and `useSearchParams` (and usePathname on dynamic routes) forces the whole (main) tree into CSR; the sheet's sign-in link href is likewise built from `window.location` in an effect. Login integration is a trimmed L1: widened subtitles only ("Sign in to manage your listings and saved gowns" / "Sell your gowns or save the ones you love"). The spec's `from=wishlist` AuthScreen context line ("Your wishlist comes with you") was built then REMOVED at user request as redundant, along with all its plumbing (the `from` searchParam on AuthScreen + login/register pages, the `&from=wishlist` on the drawer sign-in link) — do NOT re-add it. The separate `?wishlist=open` auto-reopen param stays; safePostAuthPath already preserves it on the internal `next` (verified).

- [07-24-2026] decision: Field-error VISUAL convention — an inline validation error reads ONLY as the red message below the field: NO red input border, NO red ring, NO red typed text (user directive: "no red borders anywhere"). Applied at the shared form-wrapper layer (`src/components/form/`), NOT globals.css (per the 07-13 note, unlayered attribute overrides don't emit under Turbopack — use className+utility). Three pieces, all in `src/components/form/`: (1) `FORM_CONTROL_QUIET_INVALID_CLASS` (constants.ts) neutralizes `aria-invalid:border-destructive`/`ring-*` → `aria-invalid:border-input aria-invalid:ring-0`, added to `TextInputField`, `TextareaField`, and `SelectField`'s trigger (controls that carry `aria-invalid` on themselves); (2) `FORM_GROUP_QUIET_INVALID_CLASS` does the same via `has-[[data-slot][aria-invalid=true]]:…` for the `InputGroupField` container (which styles itself from an invalid descendant); (3) `FormField` adds `data-[invalid=true]:text-foreground` on the `Field` to cancel `ui/field`'s `data-[invalid=true]:text-destructive` red text — the `FieldError` message keeps its OWN red (set on that element). CRUCIAL: both quiet-classes RE-ASSERT the focus ring with `!` important (`focus-visible:border-ring! focus-visible:ring-3! focus-visible:ring-ring/50!`, and the `has-…:focus-visible:*!` equivalents) because `aria-invalid:ring-0` also swallows the focus-visible ring — without this a focused invalid control had NO focus indicator (a11y regression). Verified live via getComputedStyle: resting invalid = normal `--input` border + no ring + ink text + red `FieldError`; focused invalid = gold `--ring` 3px ring + gold border (NOT red); `aria-invalid="true"` retained. Auth fields pass no `error`/`invalid`, so they never trip any of this.
