- [07-03-2026] decision: Set-only listings store no seller-entered per-size price. The form hides the per-size price inputs when "sell as set only" is checked (ListingSizeRow `showPrice`; unchecking clears row prices so switching to individual forces re-entry), and the server (variantRowsPayload in sell.ts) stamps every variant's `price = listings.bundle_price`. This keeps the variant-level browse price filter (MEMORY 07-02) UNCHANGED: a set-only listing filters as a single-priced item at its set total (a $400 set is excluded by a max-$200 filter), while individual/either keep real per-size prices so the size+price coupling still holds (a $600 size-8 stays excluded by max-$400). No schema migration — `listing_sizes.price` stays NOT NULL. Chose this over (A) a denormalized `listings.min_price` column — rejected because it decouples size from price (would wrongly surface the $600 size-8 via a cheaper size in the same listing) — and over (B) a Postgres RPC/view — rejected as a heavy rewrite of the count/pagination/filter layer; both became unnecessary once set-only variants carry the set total. `bundle_price` stays on `listings` as the display source of truth (and the only home for `either`'s discount); the mirrored variant price is filter-only and never shown. Invariant "set_only ⇒ every variant.price == bundle_price" is app-enforced on create + update (variantRowsPayload runs on both; a CHECK can't reference another table and a trigger was avoided for simplicity), and read/delete need nothing extra (read is consistent by construction, delete cascades).

- [07-06-2026] decision: Multi-write listing mutations are atomic via Postgres RPCs (security invoker, `set search_path=''`, granted to authenticated), NOT client-side supabase-js sequences — because supabase-js talks to stateless PostgREST and can't hold a transaction across calls. `mark_listing_sold(p_listing_id)` (migration 010) flips listings.status + all listing_sizes.status in one tx (mirrors the old `.eq(user_id)` guard: `where user_id = auth.uid()` + row_count=0 → "Listing not found"). `update_listing_with_variants(p_listing_id, p_listing jsonb, p_variants jsonb)` (migration 011) updates the listing row + reconciles variants (delete removed / update price+sort_order preserving status / insert new via jsonb_to_recordset), replacing the TS `syncListingSizes` diff (now deleted, along with ExistingVariant type + the `sizes` embed in updateListing's existing-row select). sell.ts's updateListing now uploads images → calls the RPC → deletes ORPHAN images only AFTER the atomic commit (was before, which orphaned them on a mid-sync failure). Image upload/cleanup stay in the action (storage can't join a DB tx). Rejected an ORM (Drizzle/direct pg) that would allow TS-side transactions: conflicts with AGENTS "no ORM", loses RLS as the free ownership gate (direct conns bypass RLS), adds a 2nd data-access path + serverless pooling — disproportionate for two low-frequency partial-write windows. Verified with a BEGIN…ROLLBACK smoke test in the Supabase SQL editor (all checks PASS: variant diff, sold-variant status preserved, atomic rollback of listing row on a failed variant insert, mark-sold cascade, non-owner rejection). - [07-24-2026] decision: Field-error VISUAL convention — an inline validation error reads ONLY as the red message below the field: NO red input border, NO red ring, NO red typed text (user directive: "no red borders anywhere"). Applied at the shared form-wrapper layer (`src/components/form/`), NOT globals.css (per the 07-13 note, unlayered attribute overrides don't emit under Turbopack — use className+utility). Three pieces, all in `src/components/form/`: (1) `FORM_CONTROL_QUIET_INVALID_CLASS` (constants.ts) neutralizes `aria-invalid:border-destructive`/`ring-*` → `aria-invalid:border-input aria-invalid:ring-0`, added to `TextInputField`, `TextareaField`, and `SelectField`'s trigger (controls that carry `aria-invalid` on themselves); (2) `FORM_GROUP_QUIET_INVALID_CLASS` does the same via `has-[[data-slot][aria-invalid=true]]:…` for the `InputGroupField` container (which styles itself from an invalid descendant); (3) `FormField` adds `data-[invalid=true]:text-foreground` on the `Field` to cancel `ui/field`'s `data-[invalid=true]:text-destructive` red text — the `FieldError` message keeps its OWN red (set on that element). CRUCIAL: both quiet-classes RE-ASSERT the focus ring with `!` important (`focus-visible:border-ring! focus-visible:ring-3! focus-visible:ring-ring/50!`, and the `has-…:focus-visible:*!` equivalents) because `aria-invalid:ring-0` also swallows the focus-visible ring — without this a focused invalid control had NO focus indicator (a11y regression). - [07-24-2026] decision: The wishlist `WISHLIST_MAX_ITEMS` (50) cap is a PER-DEVICE / PER-BATCH bound (localStorage size + sync-payload size), NOT a hard account-total invariant. The signed-in account total can legitimately exceed 50: the sign-in union merge (mergeWishlist) folds a device's items into an account that may already hold others (each side ≤50, union up to ~2x), and `mergeItemsSchema.max(50)` caps only the incoming batch, not the union; `addToWishlist` has no server-side count guard either. Accepted as-is (Cursor Bugbot "Merge union breaks fifty cap", Medium): worst case is a user seeing a few extra of THEIR OWN saved gowns and being blocked from further LOCAL adds until they drop back under 50 (self-corrects). Revisit only if the cap becomes a real billing/storage limit rather than a UX bound.

- [08-03-2026] decision: Post-auth routing distinguishes "asked for nothing" from "asked for /dashboard". `safeNextPath()` returns null when nothing usable was requested; `safePostAuthPath()` is `safeNextPath(next) ?? Keep the guard only on files every test always mocks out wholesale (`src/lib/stripe/client.ts`, `src/lib/supabase/service.ts` — real bodies never execute under a `vi.mock`); omit it on plain config/helper files that need direct unit coverage (`src/lib/listing-fee.ts`).

- [07-27-2026] never: Postgres grants EXECUTE to PUBLIC by default on every new function, so `grant execute … to service_role` alone does NOT restrict anyone — a security-invoker RPC with no internal `auth.uid()` guard (e.g. `record_listing_payment`) stays callable by `authenticated`, and its inner writes run under the caller's RLS (a seller could flip their own `pending_payment` listing to `active` for free). Any service-role-only function must `revoke execute … from public` before the grant (folded into migration 003 + schema.sql).

- [08-02-2026] never: Never pass a `lucide-react` icon component (or any component reference) as a PROP from a Server Component to a Client Component. Lucide icons are `forwardRef` objects; the RSC serializer throws and the error boundary swallows the page — it type-checks and only fails at runtime. Safe when both sides are client (`ConfirmActionButton`) or the consumer is a Server Component. Pass a string key and resolve from a map inside the client module (`ADMIN_ACTION_ICONS`).

- [08-02-2026] never: Do not try to fix a `notFound()`-thrown-during-render title by rendering a literal `<title>` in `not-found.tsx` or by calling `notFound()` from `generateMetadata`.
